Detailed Description

Explicit numeric, character, and byte conversions.

A conversion policy is an optional second argument that explicitly permits a particular kind of precision loss. For example, to_int(3.75, conversion::truncate) permits discarding the fractional part and returns 3. The available policies are cljonic::core::conversion::truncate and cljonic::core::conversion::nearest; their permitted conversion directions are described below. Matching preflights accept the same second argument, for example can_to_int(3.75, conversion::truncate) returns true because the truncated value, 3, fits in int.

When only the value is supplied, as in to_int(3.0), a numeric conversion succeeds only if the destination can represent the supplied value exactly, without rounding, discarding a fractional part, or wrapping. This checks the particular value, not whether every value of its source type would fit:

  • Integer-To-Integer: the value must fit the destination's range; negative values cannot convert to unsigned types.
  • Floating-To-Integer: the value must be finite, have no fractional part, and fit the destination's range. For example, to_int(3.0) succeeds, while can_to_int(3.5) returns false.
  • Integer-To-Floating and Floating-To-Floating: the destination must preserve the value without rounding. For example, to_float(1.5) succeeds; on a float with 24 binary precision digits, can_to_float(16777217) returns false because that integer cannot be represented exactly.

NaN and infinity are rejected, including when source and destination have the same type. Floating-To-Floating conversions preserve the sign of zero when the destination supports it. For example, with an IEEE 754 float destination, to_float(-0.0) returns negative float zero, and std::signbit(to_float(-0.0)) returns true. If the destination cannot represent negative zero, converting negative zero fails. Both signs of floating zero convert to integer zero. Integer zero converts to positive floating zero. A failed exact conversion follows the failure behavior below; it does not silently choose a rounded result.

Select conversion::truncate only for Floating-To-Integer truncation toward zero. Select conversion::nearest only for Integer-To-Floating or different-floating-type Floating-To-Floating conversion; it rounds to nearest with ties to even. Omit the policy for exact-same-type conversions and Integer-To-Integer conversions. Neither policy is accepted for character or byte conversions.

The matching can_to* functions return true when the corresponding conversion would succeed, otherwise false, even during constant evaluation.

Unsupported types or policy combinations fail compilation with a cljonic-specific error message naming the operation and explaining its permitted inputs and policies. This applies to both conversions and preflights: can_to_float('A') does not return false; like to_float('A'), it fails compilation because char sources are not supported for floating destinations. Likewise, to_int(3.5, conversion::nearest) fails compilation because nearest rounding is not supported for integer destinations; use conversion::truncate to deliberately discard the fractional part.

Supported Source and Destination Types

Here, "non-character integer" means short, int, long, long long, or their unsigned counterparts, including aliases such as std::size_t. Plain char has its own conversion rules below. In C++, char, signed char, and unsigned char are three distinct types: a platform where plain char is signed does not make it the type signed char.

  • Non-Character Integer Destinations (such as to_int and to_uint): accept non-character integers, supported binary floating-point values, and plain char. Every successful result preserves the supplied value unless an allowed floating-to-integer truncation policy is selected, and must fit the destination's range. For a char source, omit the policy: to_int('A') returns its native numeric character code (65 on ASCII-compatible systems), and to_int('\0') returns 0. This is not digit parsing: to_int('7') returns the character code, not the number 7. Negative plain-char values remain negative when converted to a signed integer; conversion to an unsigned integer fails rather than wrapping.
  • Floating Destinations (such as to_float): accept non-character integers and supported binary floating-point values, but not char or std::byte.
  • Plain Char and Byte Destinations (to_char and to_byte): accept non-character integers, plain char, and std::byte, subject to the value checks below; floating-point sources are not accepted.

Bool, signed char, unsigned char, wchar_t, char8_t, char16_t, char32_t, application enums, pointers, and user-defined types are not supported as sources or destinations by these conversion APIs. This exclusion does not include plain char or std::byte, which are supported exactly as described above. Type aliases follow their underlying type; for example, std::uint8_t is unsupported when it aliases unsigned char.

The to_char free function accepts non-character integers, char, or std::byte and checks the value against std::numeric_limits<char>::min() through std::numeric_limits<char>::max() before conversion. NUL and all representable non-ASCII values are allowed; every char source is returned unchanged. An out-of-range value fails rather than wrapping. The to_byte free function accepts non-character integers or plain char whose numeric value is in 0..UCHAR_MAX, including zero, and returns the corresponding std::byte. Negative char values fail rather than being reinterpreted as unsigned byte codes. A std::byte source is returned unchanged.

These are low-level conversions, independent of cljonic's String character-validity policy. to_char(0) succeeds with NUL, but character_is_valid still returns false for NUL, and String still enforces its non-NUL ASCII content range (1..127). Character and byte range failures use ConversionError::out_of_range. Matching preflights check the same input rules, and generic to<T> and can_to<T> follow the same rules for their selected destination.

An invalid value of a supported type is different from an unsupported type or policy: can_to_int(3.5) compiles and returns false because exact conversion would discard a fractional part; to_int(3.5) follows the conversion failure behavior below.

Runtime Conversion Failure Modes

These conversion APIs have a compile-time configuration that selects what happens when a supported conversion fails its value checks at runtime. This is not a general cljonic build mode or a per-call rounding policy: it controls conversion failure handling only. Successful conversions and the input-validation rules are the same in both modes.

  • Normal Mode (default): leave CLJONIC_CONVERSION_DIAGNOSTICS undefined or define it as 0. A failed runtime conversion returns a fallback: the destination's maximum integer value, maximum finite floating value, all-bits-set std::byte, or NUL char. A fallback can also be a valid conversion result, so use the matching can_to* preflight when failure must be distinguished from success. No diagnostic error is stored, and cljonic::core::conversion_error() returns cljonic::core::ConversionError::none.
  • Diagnostic Mode: define CLJONIC_CONVERSION_DIAGNOSTICS as 1 before including cljonic, or use the compiler definition -DCLJONIC_CONVERSION_DIAGNOSTICS=1. Use the same setting in every translation unit in the program. Your application must define [[noreturn]] void cljonic::core::conversion_failure_handler() noexcept. A failed runtime conversion records its cljonic::core::ConversionError, then calls this handler instead of returning a fallback. The handler must not return or throw; the application decides how to stop execution. The handler can inspect the recorded error through cljonic::core::conversion_error(). The library provides no default handler or error-reset operation; successful conversions do not clear a recorded error.

Other values of CLJONIC_CONVERSION_DIAGNOSTICS are rejected at compile time. In either mode, preflights return true or false without recording an error or invoking the handler; any previously recorded error is preserved. Unsupported source types, destinations, or policies still fail compilation in either mode.

These modes apply only to runtime evaluation. If a failed conversion is required to be evaluated at compile time, for example in a constexpr variable initializer, compilation fails: no fallback is returned, no error is recorded, and no handler is called. A failed value preflight in a constant expression simply returns false. Supplying a literal argument alone does not require compile-time evaluation.

Examples

#include "cljonic.hpp"
using namespace cljonic;
using namespace cljonic::core;
int main() {
static_assert(to<double>(42) == 42.0);
static_assert(to_int(3.75, conversion::truncate) == 3);
static_assert(to_float(16777217, conversion::nearest) == 16777216.0F);
static_assert(to_char(65) == 'A');
static_assert(to_int('A') == static_cast<int>('A'));
static_assert(to_int('\0') == 0);
static_assert(to_char(0) == '\0');
static_assert(!can_to_int(3.75));
const double value = 12.0;
if (!can_to_int(value)) {
return 1;
}
return to_int(value) == 12 ? 0 : 1;
}

This separate diagnostic-mode program deliberately attempts an inexact conversion. Its application-defined handler checks the recorded error and stops the program with exit code 2 for precision loss, or 1 for another conversion error. The call never returns a fallback. For a multi-file application, enable the same diagnostic setting in every translation unit and define the handler in exactly one.

#define CLJONIC_CONVERSION_DIAGNOSTICS 1
#include "cljonic.hpp"
#include <cstdlib>
using namespace cljonic;
using namespace cljonic::core;
namespace cljonic::core {
[[noreturn]] void conversion_failure_handler() noexcept {
if (conversion_error() == ConversionError::precision_loss) {
std::_Exit(2);
}
std::_Exit(1);
}
} // namespace cljonic::core
int main() {
const double measured_count = 3.75;
const int count = to_int(measured_count);
return count == 3 ? 0 : 1;
}
